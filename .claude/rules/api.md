# API

- Every route declares who may call it, exactly once, on the handler (`apps/api/src/modules/access/access.decorators.ts`). A route with no declaration or with two is never run (500) and fails the harness.
  - `@Public()`: works without sign-in. A decision for the owner; the route goes into `PUBLIC_ROUTES` in `public-routes.test.ts` with a reason.
  - `@AnySignedIn()`: every signed-in account, whatever its roles. Only for a route that acts on the account of the session and never on one named in the request.
  - `@Requires(area, action)`: a role that the permission table (`PERMISSIONS` in `packages/shared/src/permissions.ts`) gives the action in the area. A new area is a new entry of the table with a row for each of the 15 roles; changing the table needs the owner (`CLAUDE.md`).
- A `@Requires` route works for one branch, named by the request in the header `X-Branch-Id`. The route reads `@CurrentAccess() access: Access`, passes `access.branchIds` to `Transactions.run` and `access.assignmentId` to `audit.record`. A branch never comes from the path, the query or the body. `@Requires(area, action, { branch: 'none' })` is for school-wide work only (a branch, an account): no header, and `access.branchIds` is empty.
- The guard allows a request when any current assignment of the account permits it: a role with a branch counts in that branch only, the Super Admin and the Senior Head Teacher in every branch. When several assignments permit, the first by id is the one named (`access.assignmentId`); the rule is in `permission-check.ts` and is the same for every route.
- Every new or changed route is added by hand to `ROUTE_ACCESS` in `apps/api/src/modules/access/route-permissions.test.ts`, with the roles that may call it and whether it works for the branch of the request or for none. A route with a permission never carries an `@AllowedBefore...` mark; those are for the own sign-in only (`STEP_ROUTES` in the same test). The harness calls it as each of the 15 roles, without a role and without sign-in, in the own and in another branch.
- Every route that takes the id of a branch record in its path has a route test that sends the id of another branch's record and of an unknown one, expects 404, and checks that the record and the audit log did not change (found missing on "Start year" by the permission review of task 1.3).
- The same holds for an id in the body (a slot type in a list, a template named by a setting) and for every route that runs another route's change, such as a preview: one 404 test per id, for another branch's and an unknown one, with the rows of both branches and the audit log unchanged (found missing on the version and preview routes by the permission review of task 1.5).
- The guard decides role and branch only. Check scope (subjects, class, own lessons) in the route for every request, and test it there.
- A route that decides a request (unlock, plan edit) calls `refuseOwnRequest(access.accountId, requestedBy)` (`own-request.ts`): nobody approves their own.
- Validate input with schemas from `packages/shared`. Return the one shared error shape.
- A route reads its input only through `ValidBody`, `ValidQuery`, `ValidParams` and `RequestKey` (`apps/api/src/http/schemas.ts`). `Body`, `Query`, `Param`, `Headers`, `Req`, `Request` and the other raw request decorators of `@nestjs/common` (the list is in `eslint.config.js`) may be imported only inside `apps/api/src/http/`; a lint rule refuses them elsewhere. `createParamDecorator`, `assignMetadata` and `REQUEST` of `@nestjs/core` (also as the text `'REQUEST'`) are refused the same way, except in `session.guard.ts` and `permission.guard.ts`: a route gets the session, the access and the request id from `CurrentSession`, `CurrentAccess` and `RequestId`.
- The API reads JSON bodies only: a request with a body of another type, or of no type, is answered 415 `unsupported_media_type` before it is read (`apps/api/src/http/json-only.ts`). A route that takes files needs a declared exception there; ask first. Every answer carries `Cache-Control: no-store`.
- Code of the application imports nothing from `apps/api/src/testing/` and never `requiresInTable`; a lint rule refuses both outside tests and `src/testing`.
- Check permission and scope before `RequestKeys.runOnce`, on every request: a repeat does not run the work, so a check inside the work would be skipped.
- A change that must be safe to repeat (publish, close, offline entries) takes `@RequestKey()` and runs inside `RequestKeys.runOnce` in the same transaction as the change. The request names its account: `accountId: access.accountId` (or the account of the session), never one from the path or the body. A key belongs to that account; another account that sends it gets 409 `request_key_reused`. A scope never begins with `job:`; that is for `runJobOnce`, which only the runner of jobs calls.
- Use the injected clock. Do not call `Date.now()` or `new Date()` in business code.
- Write to the audit log in the same transaction as the change. Enqueue jobs in that transaction too: `jobs.enqueue(transaction, definition, { branchIds, data })` (`apps/api/src/jobs/`), with ids only in `data`.
- A change that the spec says is notified (a timetable change, a substitution, a lock, a plan window) calls `notifications.send(transaction, { kind, data, branchId, accountIds })` (`apps/api/src/modules/notifications/`) in the transaction of the change; the audit entry of that change covers the event. A new kind goes into `NOTIFICATION_KINDS` (`packages/shared/src/notifications.ts`) with the schema of its data and its text under `notifications.kinds.<kind>` in the three locale files of the web app; `data` holds what the text needs and nothing else. No route sends a notification on request.
- A job handler decides from stored moments and the injected clock, never from the fact that it was triggered; a job can run late or twice.
- After changing a route, run `pnpm api:client` so the web client matches.
