# Migrations

Read `docs/spec/edge-cases/developer-rules.md` before writing a migration.

- A migration is a new numbered SQL file. Never edit a migration that is already merged.
- Never drop or weaken a constraint, index or trigger named in the developer rules. Ask first.
- A change that rewrites or locks a large table is split into two steps.
- Each migration grants `sodiq_app` its rights table by table; no default privileges.
- After a migration, run `pnpm db:migrate` and `pnpm db:codegen` and commit the generated types.
- A moment that a business rule compares (locks, windows, exemption ends, lesson times) is written from the injected clock, never from SQL `now()` or `current_timestamp`. `default now()` is allowed only for bookkeeping columns that no rule reads.
- Audit and history tables are append-only: the application user has no update or delete rights on them.
- Every table in schema `public` is classified. Either it belongs to a branch: `branch_id uuid not null references branches (id)`, row security on, and exactly the `branch_filter` policy written in `db/migrations/0002_branches_branch_filter_request_keys.sql`, with no other policy. Or it is school-wide and is named, with a one-line reason, in `SCHOOL_WIDE_TABLES` in `apps/api/src/database/catalog.test.ts`. A table in neither group fails that test. A school-wide table that names a branch all the same (today only `assignments`) is also named in `SCHOOL_WIDE_WITH_BRANCH` there: its `branch_id` references `branches (id)` and it has no policy. Adding a table to either list is a decision for the owner: ask first.
- Views and functions must not bypass the branch filter. Every view is created `with (security_invoker = true)`. No materialized views. No function is `SECURITY DEFINER` unless it is named with a reason in the allow-list in `catalog.test.ts`; ask first.
- Business code gets its transaction from `Transactions.run(branchIds, work)` (`apps/api/src/database/transactions.ts`), which sets the branch filter for that transaction only. Never set `app.branch_ids` anywhere else, and never with `set` or with `set_config(..., false)`; a lint rule refuses the name outside `transactions.ts`.
- Foreign keys and unique constraints are not filtered by branch. A unique constraint on a branch table includes `branch_id`, and an id that arrives in a request is checked against the branch before it is used in a foreign key.
- To re-apply an unmerged migration locally, ask the owner before dropping or resetting anything in sodiq_dev, even when the tables are empty.
- A check that a row was written by the current transaction (`xmin` compared with `pg_current_xact_id()`) also matches a row the transaction only updated; when the rule is "inserted by this transaction", also compare its `default now()` column with `now()`, the start of the transaction (an identity check, not a moment a business rule compares) (found by the spec review of task 1.6 on `Transactions.enterCreatedBranch`).
- A row lock taken in a query with a condition (`... where status = 'closed' for share`) locks only the rows that meet the condition: a guard that must make a concurrent change wait locks the row first, whatever its state, and reads the state afterwards (found by the spec review of task 2.1 on the closed-year guard of `subject_quarter_weights`).
- A counter or round that decides which rows count (`weights_round` of `subjects`) is guarded in the database: it only grows, and the rows it decides are written only in the current value, so that no old row comes back into force without new values and an audit entry (found by the spec review of task 2.1).
- A rule that a check waives for rows out of service (a person who left, an archived record) is checked again when the row comes back into service (a re-hire, a restore), under the same row locks as the check that waived it (found by the spec review of task 2.2a: a subject lost a grade while its teacher had left, and the re-hire brought the teacher back with it).
  - The re-check covers every rule the waiver skipped, not only one of them (found by code round 1 of the review of pull request #53: a re-hire checked the subjects but not the archived divisions and departments).
  - A row out of service today with a return to service planned after today counts as in service for the checks that waive it, or the return escapes every check made before its date (same round: "out of the school" became `staff_out_for_good`).
  - A function that tells whether a row is out of service must not depend on what the membership filter lets the request see (same round: the main branch link of a person was invisible from a further branch).
- A condition on another table read in the statement that waits for a row lock (`select … for update` with `exists (…)`) keeps the snapshot of before the wait: PostgreSQL re-checks the locked row only when it was updated. A change that removes the other row without updating the locked one (a branch link removed under the record's lock) slips past it; read the other row again after the lock, in a statement of its own, `for share` when it must stay (found by the spec review of task 2.2b).
- A read of `assignments`, the school-wide table that names a branch and has no policy, keeps in code to `access.branchIds` and to the rows with no branch for every reader who is not the Super Admin; the branch filter does not do it there (found by code round 1 of task 2.3a).
- A rule that the database also compares with `app.now` (a start, an end, a role in force) reads the moment from `transactionMoment(transaction)` (`apps/api/src/database/transactions.ts`) in code, never from `clock.now()`, so that the code and the database compare the same moment (found by code round 1 of task 2.3a).
- A row inserted under a savepoint (`Assignments.give`) carries the id of the subtransaction in `xmin`, also after the savepoint is released, so `xmin = pg_current_xact_id()` never matches it: "inserted by this transaction" is a column `xid8 default pg_current_xact_id()` (`day_template_versions.created_xact`, `assignments.written_xact`), which gives the top-level id inside a savepoint too and does not change on an update (found by the plan review of pull request #63).
- Two writes that can claim the same unique value (a create and a correction of a UID) take the index entries in the same order, the one both meet first written first, so that the second waits and is refused rather than deadlocked; the pair is tested in both directions (found by the spec review of task 2.4a).
- A guard that fires on the columns of one route (`update of` the edit's columns) lists only columns that no other route writes, or every route that writes one of them is checked against it and tested (found by the spec review of task 2.5a: the return of a student writes the grade).
- A delete whose cascade removes rows of a later table (the links of a student) keeps those rows in the audit entry of the delete, and writes the entries of what the cascade changes elsewhere (a relative archived), decided under the same locks as the route that changes them directly (found by the spec review of task 2.5a).
- A mirror that ends the rows of a parent record and brings them back when the parent's end is taken back (`assignments_class_tutors_end`) leaves alone the rows another cause ended or withdrew (an empty range keeps its cause), and brings back only rows whose own record is still in service (an active class in an open year); a withdrawn row is final for the application too (found by the spec review of task 3.1a).
- A shared schema that a check of the database repeats is never wider than the check: a character class such as `\p{N}` or `\p{L}` in the schema matches what the check's `[:digit:]` or its plain list matches, or is narrower, with a test of a value between them (`Oxford²`); otherwise the database's refusal reaches the route as a 500 (found by code round 1 of task 3.1a).
- The audit entry of a change whose cascade or mirror writes rows of other branches (a role end school-wide) reads those rows past the branch filter, ids and moments only, not through the transaction that may see one branch (found by code round 1 of task 3.1a: `class_tutor_ends`).
- A change that locks a row FOR SHARE and then writes a row whose trigger locks the same row FOR UPDATE upgrades its lock: two such changes at the same moment deadlock. Take the strongest lock the change will need first, in the order of the id, and test two of them on one row (found by the spec review of task 3.1b: two cancels of a leaving in one class).
- Rows given back by taking back a change that cut them (a leaving) never overlap: each comes back to the start of the next one given back when that comes before its own end, and a test runs a cut, its taking back, a second cut and its taking back (found by the browser test of task 3.1b).
- An audit entry that one change writes in several branches carries personal values (fields filled, values left behind) only in the branch where the plan makes them readable; every other branch's entry holds ids, UIDs, dates and rows, and a test reads each entry's content, not only the branches it is in (found by the permission and spec reviews of task 3.3d).
- PostgreSQL locks the row an UPDATE changes before its BEFORE ROW triggers run: a lock of a shared parent row taken in such a trigger comes after the row lock, and two updaters of two rows deadlock there. Take the shared lock in a statement before the write, or in the commit check (an advisory lock of the parent), never in a before-row trigger (found by the build of task 3.4b).
- A same-moment test of a deferred check makes the held side run its check first (`set constraints <name> immediate`), sees the other side wait in `pg_locks`, and asserts the code the waiting side gets; a held side whose check runs only at its own commit proves an order, not the lock the check takes (found by the spec review of task 3.4b).
- The two sides of a same-moment test of an advisory lock meet on no row and no index besides that lock (a unique index both insert into, a row both update): otherwise the second side waits there, `pg_locks` shows that wait, and the test passes with the lock removed (found by the spec review of task 5.1a: two group lessons of one class met on the block's class claim).
- A same-moment test that waits for a lock in `pg_locks` counts only the waits of its own test database (`join pg_stat_activity a on a.pid = l.pid where a.datname = current_database()`): `pg_locks` is the whole cluster, and in CI the test files run at once, so a wait in another file's database ends the wait too early (found on CI of task 3.6c-2: `account-access.test.ts` committed its held side before the request had signed in, and the request was answered 401).
- A row that waives a claim or a check (a class out of a block for an exam) is honoured only while every condition that justified it still holds, read each time the claim is computed (the exam stands, still seats the class, still overlaps the block), and a write of any table those conditions read recomputes the claim; a check run only when the waiving row is inserted lets it outlive its reason (found by the spec review of task 5.1b on `lesson_block_class_outs`).
- A rule between a child row and a column of its parent (a group's subject against its exam's), checked on the child's insert and on the parent's update, is checked again after the parent row is locked, in a statement of its own: a before-insert trigger that read the parent before the parent's update committed passes on the old value, and the parent's deferred check cannot see the uncommitted child (found by the spec review of task 5.1b on `exam_group_subject`).
- A path of a trigger that waives checks for one kind of write (a join that takes over another row's days) holds the row at the commit to exactly what justified the waiver (the joined rows' days and end), and the waiver of a commit check covers only the event of that write; a waiver keyed on "something of that kind happened in this transaction" lets the row take anything (found by the spec review of task 3.5c).
- A migration that changes how rows are written handles every shape the earlier code wrote, emptied rows included, and its test writes the rows the way that code did (ends, causes, links), not a simpler shape that passes the same assertions (found by the spec review of task 3.5c).
- A row lock of `branches` `for update` conflicts with the `for key share` that every insert into a branch table takes for its `branch_id` (an audit entry too): a change that holds the branch row and then waits for another row deadlocks with a change that holds that row and then writes its audit entry. Lock the other rows before the branch row, and test the pair with a held side that writes its audit entry (found by code round 1 of task 3.6b-2: a withdraw of a planned placement against a year edit).
- A write that adds a row referencing a record another change holds (a cause of a draft written by a setup change that holds its branch, room or staff row `for update`) must not meet a `for update` lock of that record taken in the other order: lock a parent whose key never changes `for no key update`, which still excludes other writers but not the `for key share` of a child's foreign key, and test that nothing waits on that row while the other side is held (found by the spec review of the plan of task 5.5a-3b-1: a calendar change and a draft write deadlocked through the branch and the version).
- A write that starts inserting rows with foreign keys to parents (dated lessons naming a class, a teacher, a room) behind a lock other changes also take (the year's versions) is checked against every change that holds one of those parents `for update` and then reaches the same lock (an archive of a class that follows its Tutor lessons): take those parents `for key share` before the shared lock, and test each such pair in both orders (found by code round 1 of the review of pull request #152: an archive of a class and a publish deadlocked).
- A value moved from a record to its rows (`relaxed` of a substitution, now per lesson) has a test in which the record's value and a row's value differ and the outcome depends on which one is read; a fixture where both agree passes whichever the code reads (found by the spec review of the code of task 5.7b-2).
- A same-moment test that proves two writers take rows in one order holds the held side after its first write only, and the other side sends its rows in the opposite order: a held side that has written everything makes the other wait on whatever it meets first, and the test passes with the sort removed (found by the spec review of the code of task 6.1a).
- A test fixture that dates the quarters of a year (a lesson needs its quarter's dates) changes the year for the file's other tests: a dated quarter moves the ends of their rows. It uses a branch and year of its own where the test allows, and the whole file is run after it is added, not the one test (found by the spec review of the code of task 6.1a: a merge test went red after a journal test).
- A restore that inserts kept rows again (a forced delete's store) checks each unique key the rows carry against what was written while they were away (a plan link, a place taken by a first write or an add), resolves it as the plan decides (the row back without the link, at a free place) or refuses it with a code of its own, under the same locks as the writes that take those keys; a route test takes the key meanwhile and restores (found by code round 1 of task 8.1: a restore answered 500 on a unique index).
- A value that a trigger requires on each write (a reason, the quarter a change takes effect from) is moved by a BEFORE trigger from the row into a setting of the transaction and the column cleared, so the next write that leaves it out is refused, never passed on the value an earlier write left; a test writes twice and leaves it out the second time (found by the spec review of the code of task 8.2).
- A trigger on a row that an `on update cascade` moves (a comment following its work's lesson) lets the cascade through by what changed (`new.lesson_id is distinct from old.lesson_id` with the row's own values unchanged), with no version, moment, author, history line or check of the target; a test moves the parent where a check of the row would refuse (found by code round 1 of task 8.2).
- A function asked once per row of a read (a check per student per lesson) is PL/pgSQL with a cheap test first, and the read narrows the rows in a `materialized` step before it calls the function: a SQL function with `set search_path` is never inlined, and the planner orders the conditions of one level by cost, so a costly function runs before a cheap filter of the same `where` (found by the real-size run on CI of task 8.5: a quarter journal took 5.6 s).
