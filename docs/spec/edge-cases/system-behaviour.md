# Edge cases: system behaviour and failures

> Part of the Sodiq School platform spec, baseline of 3 October 2026 (document revision 88).
> Index and reading order: `docs/spec/00-index.md`. Where an edge-case file is more specific than a module file, the edge-case file applies.

| Case | Rule |
| --- | --- |
| A background job fails half-way, or runs twice. | Every job can be repeated safely. A job is recorded together with the data change that caused it, so it cannot be lost between the two. Nothing that cannot be rebuilt lives only in the job queue. |
| Report totals are two minutes behind the journal. | The journal row, the bottom row and student results are always calculated from the entries themselves. Prepared totals for reports show "updated at". A page that finds them behind calculates from source and shows "updating". |
| The nightly check. | It recalculates open journals and stored final results. A difference alerts the developer and blocks closing that journal. A check that did not run also raises an alert. |
| A publish takes a while. | Users see a banner. Timetable changes for the affected dates wait; reading continues. The target is under 60 seconds for a branch. |
| A release goes out at 19:00; a tab opened at 14:00 sends old-format entries next morning. | Every request carries the application version. Entries from the previous version are accepted for at least one release; otherwise the page asks to reload and keeps the unsent entries. Database changes are made in two steps so that tables are never locked for long. |
| A bad release corrupts marks at 09:10 and it is noticed at 13:00. | The live system is not rolled back for this, because that would erase four hours of valid work. The backup is restored to a side copy and the damaged entries are repaired from it, with history. A full restore is only for total loss. Targets: at most 5 minutes of entries lost and service back within 2 hours. |
| The data centre or the school's internet is down during the first lesson. | A printable attendance sheet per class is prepared the afternoon before. Lesson mode opens without a connection for today's lessons and keeps entries until it returns. Afterwards the Academic Vice Principal extends the edit period for a date range for the whole branch in one logged action. A read-only switch lets people view while entering is off. |
| The timetable generator, the SMS service, email or file storage is down. | Only that function fails. Journal, timetable and sign-in never depend on them; photos fall back to initials. |
| "All present" for thirty students. | One request and one save, with one history entry per cell. |
| A whole branch's journals are exported to PDF during lessons. | A large export is a background job, one per user, taken from one consistent moment and stamped with date and "provisional" or "final". The link works for 24 hours and access is checked again at download. |
| Cell saves fail in one branch at 08:05 and nobody notices until the break. | Alerts go to a phone, per branch, for: failed or slow cell saves, a jump in refused saves, failed jobs, a failed publish or close, a nightly-check difference, a backup older than 24 hours, and far fewer first-slot lessons with attendance by 09:00 than usual. A test teacher account signs in and saves a cell in a test class every 5 minutes from 07:00. A named person is on call on school days. |
| Old classroom computers and weak Wi-Fi. | The school's machines are surveyed before building, and the oldest supported browser versions are published. Unsent entries survive a reload and a restart. The journal is tested on a computer with 4 GB of memory and on a slow connection that drops packets. |
| A Russian-language user exports a journal; a class name exists in one language only. | Interface texts exist in three languages. Subject names are required in three. Other names (classes, rooms, reasons) are shown as entered. Excel exports contain real numbers and dates. PDFs are made on the server with fonts that cover Uzbek Latin and Cyrillic. |
| A lock bug appears only at midnight on the last day of a quarter; rollover code first runs in August. | The clock can be set in tests. Required tests: the moments 23:59 and 00:00 for locks, publish start, quarter end and exemption end; a nightly full-year run (set up, publish, enter, change the calendar, close four quarters, close the year, roll over); simultaneous actions (two publishes, publish against a one-day change, closing against a cell save, a transfer against a cell save, two users in one cell); and a rollover rehearsal each July on a restored copy kept inside the live environment, under the same access rules, and deleted afterwards. |
| There is one developer, so "review by a second developer" cannot happen. | Every change passes the automated tests and an independent automated code review before release. Any change to permissions or to the calculation module also needs the owner's sign-off on a written checklist. |
| Data volume. | A rough estimate for a school of this size is 170,000 to 250,000 dated lessons, 8 to 10 million journal cells and 15 to 25 million history entries per year. Speed is tested at three times that. This is an estimate to be replaced by the school's real counts. |
